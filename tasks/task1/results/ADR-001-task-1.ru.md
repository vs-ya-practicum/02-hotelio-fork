## Целевое состояние

> [!INFO] Этот раздел содержит целевое (TO-BE) состояние системы, её требования, проблемы и решения на высоком уровне.

### Финальное состояние через год

- Полный переход на микросервисную архитектуру.
- Service mesh с автоматизированными rollouts.
- Масштабируемая Kafka-инфраструктура.
- Метрики и трассировка на каждый сервис.
- GraphQL для фронтенда.

### Требования

#### Функциональные

|  №  | Участники или системы                                                                    | Вариант использования                          | Описание                                                                                                                                                  |
| :-: | :--------------------------------------------------------------------------------------- | :--------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
|  1  | Пользователь, партнёрский канал                                                          | Поиск и просмотр отелей                        | Доступ к информации об отелях через public API во время и после миграции.                                                                                 |
|  2  | Пользователь, BookingService, UserService, HotelService, PromoCodeService, ReviewService | Создание бронирования                          | Проверка пользователя, отеля, промокода и репутации отеля перед сохранением бронирования.                                                                 |
|  3  | Клиент, API gateway                                                                      | Использование public API во время миграции     | Сохранение доступа к public API при переводе маршрутов по одной функции от монолита к вынесенным сервисам.                                                |
|  4  | Команда эксплуатации                                                                     | Миграция функции                               | Развёртывание вынесенного сервиса, передача ему маршрута и самостоятельного управления данными, восстановление маршрута монолита в период сосуществования при необходимости отката. |
|  5  | Frontend-клиенты                                                                         | Использование адаптированного для клиентов API | Использование GraphQL в финальном целевом состоянии.                                                                                                      |

#### Нефункциональные

|  №  | Требование                                                                                                                                |
| :-: | :---------------------------------------------------------------------------------------------------------------------------------------- |
|  1  | Использовать Strangler Fig: мигрировать по одному компоненту, пока монолит обслуживает не перенесённый функционал.                        |
|  2  | В ближайшей перспективе мигрировать несколько сервисов; legacy-модули не получают новый функционал.                                       |
|  3  | Каждый вынесенный сервис можно развёртывать и масштабировать независимо; он самостоятельно хранит и изменяет свои данные.                  |
|  4  | Разделять базы данных инкрементально с явной миграцией данных и переключением источника истины.                                           |
|  5  | Сохранять совместимость public API при миграции маршрутов.                                                                                |
|  6  | Обеспечить контролируемые rollout и rollback, health checks, метрики и трассировку для каждого сервиса.                                   |
|  7  | Предоставить масштабируемую платформу Kafka для нужд интеграции сервисов.                                                                 |
|  8  | Достичь финального состояния: полностью вынесенные микросервисы, service mesh с автоматическими rollouts и GraphQL для frontend-клиентов. |

### Проблемы и решения

1. **Связанная поставка и функциональная автономия**
    - Направление: постепенно выносить сервисы по шаблону Strangler Fig, пока монолит продолжает обслуживать не перенесённый функционал.

2. **Общая база данных препятствует независимому масштабированию и самостоятельному управлению данными**
    - Опции: скопировать данные и передать самостоятельное управление ими; временно писать в обе базы (dual-write); реплицировать изменения из базы монолита.
    - Направление: база данных на каждый сервис, миграция по одному набору данных за раз с явным переключением источника истины.

3. **Единый универсальный клиентский API ограничивает развитие продукта**
    - Решение: использовать gateway во время миграции и предоставить GraphQL для frontend-клиентов в финальном целевом состоянии.

4. **Недостаточная операционная устойчивость и контроль релизов**
    - Решение: начать с управляемого Kubernetes, Grafana Alloy и Grafana Cloud. Kubernetes обеспечивает среду выполнения, пробы, rollout и rollback; Grafana — метрики, логи, дашборды и алерты. Внедрить Istio позже.
    - Опции: Traefik на Docker Swarm. Отклонено. Создаёт промежуточную среду выполнения. Istio не может обеспечить целевой service mesh на Swarm, поэтому будущая переработка значительна.

## Направления миграции

| Шаг миграции                                                                                                                            | Решаемая проблема                                |
| --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1. Наладить управляемую поставку изменений: внедрить выбранные механизмы развёртывания и отката, Ingress и средства мониторинга, логирования и трассировки. | 4. Операционная устойчивость и контроль релизов  |
| 2. Настроить пограничный API-слой: поставить gateway перед монолитом, сохранив текущие клиентские маршруты.                            | 3. Универсальный клиентский API                  |
| 3. Применить шаблон Strangler: заморозить legacy-модули и выносить одну бизнес-функцию за раз с явным сервисным контрактом.             | 1. Связанная поставка и функциональная автономия |
| 4. Передавать самостоятельное управление данными при каждом выносе: мигрировать данные функции, переключить источник истины и убрать доступ к общей базе. | 2. Общая база данных                             |
| 5. Последовательно отвязать BookingService: заменить прямые зависимости на сервисные контракты по мере выноса зависимых функций.        | 1. Связанная поставка и функциональная автономия |
| 6. Развивать доставку клиентского функционала: добавить GraphQL или BFF после появления gateway и стабильных сервисных контрактов.      | 3. Универсальный клиентский API                  |

## План миграции для Задачи 1

> [!INFO] Этот раздел содержит детальный план для задания «Задача 1» и черновой план последующих шагов.

### Решения и обоснования

1. **Начать с HotelService**: HotelService — это хорошо выделенная, преимущественно read-only бизнес-функция с отдельными данными и меньшим риском выноса по сравнению с BookingService.

2. **Перенести данные вынесенного HotelService в отдельную базу**: Отделение данных отелей даёт HotelService самостоятельное управление данными и независимое масштабирование.

3. **Внедрить Kubernetes**: Управляемый Kubernetes предоставляет общую среду выполнения для параллельного развёртывания монолита и сервисов с прямым путём к Istio.

4. **Внедрить CI/CD**: CI/CD собирает версионируемые образы и воспроизводимо развёртывает их с контролируемыми rollout и rollback.

5. **Внедрить API Gateway**: Сохраняет маршруты public API и управляет направлением трафика тестировщиков в blue/green-среды и production canary-трафиком.

6. **Внедрить средства мониторинга, логирования и трассировки**: Они делают blue/green и canary-релизы наблюдаемыми и безопасными без изменения монолита.

#### План выноса сервиса

> [!NOTE]
> Этот план соответствует шаблону Strangler Fig.

Это явная последовательность сосуществования и переключения:

1. Подготовить Kubernetes, CI/CD, API Gateway и средства мониторинга, логирования и трассировки. Затем кратко заморозить релизы монолита, чтобы развернуть ту же версию монолита как `green.monolith`.

2. Оставить основной production-трафик на `blue.monolith`; валидировать `green.monolith` тестировщиками, затем направить небольшую отслеживаемую долю production-трафика на green. Переключить production-трафик на green и оставить blue для отката; снять заморозку релизов монолита.

3. Разработать HotelService по контрактам валидации отелей и бронирования монолита после переключения production-трафика на green. Вносить связанные изменения в сервис и контрактные тесты, либо отложить их до переключения.

4. Развернуть HotelService рядом с `green.monolith`. Кратко заморозить запись данных отелей, преобразовать и скопировать данные отелей в базу сервиса, затем валидировать сервис, пока `green.monolith` остаётся источником истины.

5. После переключения production-трафика на green постепенно направить только `/api/hotels` с `green.monolith` на HotelService в рамках canary-развёртывания. Вернуть этот маршрут на `green.monolith` при необходимости.

6. Изменить BookingService для использования HotelService при валидации отелей; трассировать вызов и отклонять бронирование до сохранения, если проверка не прошла.

7. Сделать данные HotelService источником истины, затем вывести из эксплуатации код, таблицу и маршрут отелей монолита после стабилизации переключения.

## Продолжение выноса сервисов

1. UserService. Имеет узкую зону ответственности — проверки статуса пользователя и чёрного списка, что снижает прямой доступ BookingService к данным пользователей. Сначала проверить аутентификацию и консистентность данных.
2. PromoCodeService. Промо-правила — отдельная функция, но расчёт цены бронирования и применимость к конкретному пользователю требуют тщательного проектирования API и консистентности.
3. ReviewService. Отвечает за отзывы и рейтинг отелей, но его рейтинг влияет на доступность бронирования — этот сценарий принятия решения необходимо сохранить.
4. BookingService. Оркестрирует остальные функции и записывает бронирования, что делает его самым рискованным по интеграции, транзакциям и управлению данными.
5. Внедрить Istio после того, как 2–3 сервиса заработают в production.
6. Добавить GraphQL BFF после появления стабильных сервисных контрактов; мигрировать frontend-клиентов с REST-маршрутов инкрементально.
